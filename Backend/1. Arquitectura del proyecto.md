# Arquitectura del proyecto

> [!tip] Contexto
> Esta nota explica el *porqué* de la estructura y el flujo de una request. Las demás notas profundizan cada pieza. Ver [[0. Backend]].

La estructura del proyecto separa tres preocupaciones: **puntos de entrada** (`cmd/`), **lógica privada** (`internal/`) y **código reutilizable** (`pkg/`). Dentro de `internal/`, la arquitectura es de **vertical slices**: cada feature (usuario, producto, ventas, farmacia...) vive en su propio módulo, sin que los módulos se importen entre sí.

## Vertical slices (rebanadas verticales)

Cada módulo de `internal/modules/<feature>/` contiene **todo** lo necesario para esa feature, junto:

```
internal/modules/user/
├── handler.go      # Recibe la request HTTP (Fiber)
├── service.go      # Lógica de negocio de la feature
├── repository.go   # Acceso a datos (GORM, Redis)
├── model.go        # Estructuras de la feature (request/response/entidad)
├── router.go       # Registra las rutas del módulo
└── module.go       # Expone el fx.Module para el contenedor DI
```

**Regla de oro:** un módulo solo habla con:
- Su propia capa interna (`handler → service → repository`).
- El shared kernel (`internal/shared`).

Nunca importes el handler de otro módulo. Si dos features necesitan lo mismo, la lógica común sube a `internal/shared` o se expone como **evento**.

> [!warning] Dependencias entre módulos
> `sales` necesita saber si un `product` existe. En vez de importar `modules/product`, `sales` usa el id y le pregunta al repositorio de productos **vía interfaz definida en `shared`** o dispara un evento `product.created` y lo consume. Así los módulos siguen desacoplados.

## Flujo de una request

```
cliente (Bruno / app)
   │  HTTP
   ▼
├─ cmd/server/main.go          → construye la app con FX (pkg/container)
│
Fiber v2 (app)
   │  middleware (recover, logger, request-id, auth, validator)
   ▼
modules/<feature>/handler.go   → parsea y valida la request, arma la respuesta
   ▼
modules/<feature>/service.go   → lógica de negocio, errores tipados
   ▼
modules/<feature>/repository.go → GORM (PostgreSQL) + Redis (caché)
   ▼
PostgreSQL / Redis
```

El **handler nunca toca la base de datos**; el **service nunca sabe que existe HTTP**. Esto permite testear cada capa por separado y cambiar transporte (gRPC, workers) sin reescribir la lógica.

## El shared kernel (`internal/shared`)

Componentes transversales que todos los módulos usan:

| Paquete | Responsabilidad |
| --- | --- |
| `config/` | Carga y validación de configuración (Viper) → [[2. Configuración con Viper]] |
| `database/` | Conexión GORM + PostgreSQL, pool y migraciones → [[5. Persistencia con GORM y PostgreSQL]] |
| `errors/` | Errores tipados de dominio (`NotFoundError`, `ValidationError`...) |
| `logger/` | Logger Zap configurado → [[9. Logging con Zap]] |
| `middleware/` | Middleware reutilizables (auth, request-id, recover) |
| `validator/` | Instancia única del validador → [[8. Validación con Validator v10]] |
| `pagination/` | Extracción de `page`/`limit`, cómputo de offset y metadata |
| `response/` | Envoltorio unificado de respuestas (`data`, `meta`, `error`) |
| `security/` | Helpers de seguridad (Argon2id, random, constant-time) |
| `jwt/` | Servicio de emisión y verificación de tokens → [[7. Autenticación con JWT y Argon2id]] |
| `events/` | Bus de eventos en proceso (pub/sub simple) |
| `clock/` | Abstracción sobre `time.Now()` para testes deterministas |
| `transaction/` | Gestor de transacciones GORM expuesto a los services |

## Los puntos de entrada (`cmd/`)

- `cmd/server/main.go` — arma el contenedor FX, arranca Fiber, registra los módulos y espera señales de apagado.
- `cmd/migrate/main.go` — ejecuta las migraciones de GORM contra la base de datos ([[12. Docker, Makefile y migraciones]]).

> [!tip] La regla de `internal/`
> El compilador de Go impide importar `internal/` desde fuera del módulo: es la forma en que el lenguaje mismo protege tu código privado. Por eso los binarios viven en `cmd/` y lo público en `pkg/`.

## Datos clave

- Un módulo = una feature completa de principio a fin (del HTTP a la BD).
- Los módulos no se importan entre sí; comparten solo `internal/shared`.
- `handler` → `service` → `repository` es un flujo de una sola dirección.
- `clock`, `events` y `transaction` existen para que la lógica sea testeable y desacoplada.
- `pkg/container` es el único lugar donde FX arma todas las piezas → [[3. Inyección de dependencias con Uber FX]].
