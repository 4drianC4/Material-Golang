# Validación con Validator v10

> [!tip] Contexto
> [go-playground/validator](https://github.com/go-playground/validator) valida structs con tags declarativos (`required`, `email`, `min`...). Es el estándar de facto en Go y se integra con los DTOs de cada módulo y con las respuestas de error → [[10. Shared kernel: respuestas, errores y paginación]].

## Instancia única (`internal/shared/validator`)

La validación es costosa de crear (compila tags): se crea **una vez** y se inyecta en todos los handlers vía FX → [[3. Inyección de dependencias con Uber FX]].

```go
package validator

import "github.com/go-playground/validator/v10"

func New() *validator.Validate {
	v := validator.New()

	// Tag personalizada para valores multi-tenant, por ejemplo:
	v.RegisterValidation("tenant_code", func(fl validator.FieldLevel) bool {
		s := fl.Field().String()
		return s != "" && len(s) <= 10
	})

	return v
}
```

## Validación declarativa en los DTOs

```go
type CreateUserRequest struct {
	Name     string `json:"name"     validate:"required,min=2,max=120"`
	Email    string `json:"email"    validate:"required,email"`
	Password string `json:"password" validate:"required,min=8,max=72"`
	Role     string `json:"role"     validate:"required,oneof=admin staff customer"`
	Age      int    `json:"age"      validate:"gte=18,lte=120"`
}
```

Tags más usados:

| Tag | Significado | Ejemplo |
| --- | --- | --- |
| `required` | campo obligatorio | `validate:"required"` |
| `email` | formato de email | `validate:"email"` |
| `min` / `max` | longitud mín/máx (string, slice, número) | `validate:"min=8,max=72"` |
| `gte` / `lte` / `gt` / `lt` | comparaciones numéricas/fechas | `validate:"gte=18"` |
| `oneof` | valor dentro de lista | `validate:"oneof=admin staff"` |
| `len` | longitud exacta | `validate:"len=10"` (teléfono) |
| `uuid` | formato UUID | `validate:"uuid"` |
| `omitempty` | opcional, pero si llega debe validar | `validate:"omitempty,email"` |
| `dive` | valida elementos de un slice | `validate:"dive,required,email"` |

## Uso en el handler

```go
func (h *Handler) Create(c *fiber.Ctx) error {
	var req CreateUserRequest

	if err := c.BodyParser(&req); err != nil {
		return response.Error(c, fiber.StatusBadRequest, "request_invalida", err)
	}

	if err := h.validate.Struct(&req); err != nil {
		return response.ValidationError(c, err) // 422 con errores por campo
	}

	user, err := h.svc.Create(c.Context(), req)
	// ...
}
```

> [!tip] No mezclar capas
> La validación de **forma** (email mal formado, campos faltantes) va en el DTO con validator. La validación de **negocio** (email ya registrado, stock insuficiente) vive en el service con errores tipados → [[10. Shared kernel: respuestas, errores y paginación]].

## Formatear los errores

`validator.ValidationErrors` es una slice de `FieldError`; se formatea campo por campo para la respuesta:

```go
func ValidationErrors(err validator.ValidationErrors) map[string]string {
	fields := make(map[string]string, len(err))
	for _, fe := range err {
		// tag golpeado + valor conflictivo real
		fields[fe.Field()] = fmt.Sprintf("fallo en '%s' (valor: %v)", fe.Tag(), fe.Value())
	}
	return fields
}
```

La respuesta final quedaría con el contrato unificado → [[10. Shared kernel: respuestas, errores y paginación]]:

```json
{
  "data": null,
  "error": {
    "code": "validation_error",
    "message": "datos inválidos",
    "fields": {
      "password": "fallo en 'min' (valor: ...)",
      "role": "fallo en 'oneof' (valor: ...)"
    }
  }
}
```

## Datos clave

- Tags declarativos en los DTOs; instancia única inyectada con FX.
- `Struct(&req)` falla con slice de `FieldError` → se transforma a mapa `campo → detalle`.
- `BodyParser` (JSON) y validator van siempre juntos en el handler → [[4. HTTP con Fiber v2]].
- Validación de forma ≠ validación de negocio: cada una en su capa.
- Registra tags personalizadas (`RegisterValidation`) cuando un tag estándar no alcanza.
