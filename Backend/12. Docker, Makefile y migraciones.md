# Docker, Makefile y migraciones

> [!tip] Contexto
> Para que el equipo arranque el backend en un comando: **Makefile** orquesta (build, test, run, migrate), **Docker** empaqueta la app y levanta las dependencias (PostgreSQL, Redis), y **migraciones** evolucionan el esquema → [[5. Persistencia con GORM y PostgreSQL]].

## Makefile

```makefile
.PHONY: run build test migrate up down lint

run:
	go run ./cmd/server

build:
	go build -o bin/server ./cmd/server

test:
	go test ./... -race -cover

migrate:
	go run ./cmd/migrate

up:       # levanta dependencias (PostgreSQL, Redis) con Docker
	docker compose up -d postgres redis

down:
	docker compose down

lint:
	golangci-lint run ./...
```

> [!tip] `go run` vs `go build`
> En dev: `make run` (compila y ejecuta). En CI/producción: `make build` y se corre el binario dentro del contenedor.

## Dockerfile (multi-stage)

Dos etapas: **compila en una imagen con Go**, **copia el binario a una imagen mínima**. El binario final no necesita toolchain.

```dockerfile
# --- Etapa 1: build ---
FROM golang:1.25-alpine AS builder
WORKDIR /app

# cachea dependencias (solo cambia si go.mod/go.sum cambian)
COPY go.mod go.sum ./
RUN go mod download

COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o /bin/server ./cmd/server

# --- Etapa 2: runtime ---
FROM alpine:3.20
RUN apk add --no-cache ca-certificates tzdata
COPY --from=builder /bin/server /usr/local/bin/server
COPY configs/ /app/configs/

EXPOSE 8080
ENTRYPOINT ["server"]
```

> [!warning] `CGO_ENABLED=0`
> Produce un binario **estático** que corre en cualquier imagen (incluida `scratch`). Algunas librerías (p. ej. `net` con DNS custom) requieren CGO; si migras a una que lo necesite, cambia la imagen base a una con glibc (`debian-slim`).

## docker-compose.yml

```yaml
services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-postgres}
      POSTGRES_DB: mi_backend
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 10

  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 10

  app:
    build: .
    ports:
      - "8080:8080"
    env_file: .env
    depends_on:
      postgres:
        condition: service_healthy   # no arranca hasta que la BD responde
      redis:
        condition: service_healthy

volumes:
  pgdata:
```

> [!tip] `env_file: .env`
> El contenedor recibe las variables `APP_*` desde `.env` local ([[2. Configuración con Viper]]). En producción el orquestador (K8s/EKS) las inyecta por secretos; el código no cambia.

## Flujo de migraciones

### 1. Estructura (`cmd/migrate/main.go`)
```go
func main() {
	cfg := config.Load("configs/config.yaml")
	db := database.New(&cfg.Database)

	err := db.AutoMigrate(
		&user.User{},
		&product.Product{},
		&tenant.Tenant{},
		&sales.Sale{},
	)
	if err != nil { log.Fatalf("migración fallida: %v", err) }
	fmt.Println("esquema sincronizado")
}
```

### 2. Comandos
```bash
make up        # 1. Postgres + Redis arriba
make migrate   # 2. Esquema al día
make run       # 3. App en :8080 → probar con Bruno ([[11. Cliente de APIs con Bruno]])
```

### 3. Flujo de trabajo con AutoMigrate

| Situación | Acción |
| --- | --- |
| Campo nuevo | añadir al modelo + `make migrate`; GORM crea la columna |
| Modelo nuevo | añadir al `AutoMigrate` + `make migrate`; GORM crea la tabla |
| Renombrar / borrar columna | **NO** con AutoMigrate: script SQL manual o migración tipo `ALTER TABLE` con backfill |

> [!warning] AutoMigrate frente a migraciones versionadas
> `AutoMigrate` no registra versiones (no hay `migrations/001_x.sql`): es idempotente y agrega. Para proyectos en producción con varias réplicas, el estándar es una herramienta versionada (golang-migrate / goose). Este stack elige simplicidad: mientras el equipo sea pequeño, AutoMigrate es suficiente y siempre se puede migrar después.

## Pipeline típico de CI

1. `make build` → compila.
2. `make test` → `go test ./... -race`.
3. `make lint` → `golangci-lint`.
4. `docker compose up -d postgres redis` → deps.
5. `make migrate` → esquema.
6. `make run` (o binario) + `bru run --env local` → smoke tests del API → [[11. Cliente de APIs con Bruno]].

## Datos clave

- Makefile = interfaz única del equipo: `run/build/test/migrate/up/down/lint`.
- Dockerfile multi-stage con binario estático (`CGO_ENABLED=0`).
- compose levanta Postgres y Redis con healthchecks; la app espera `service_healthy`.
- Configuración por `env_file: .env` (variables `APP_*`).
- AutoMigrate agrega esquema; cambios destructivos van por SQL manual.
- CI: build → test → lint → migrate → smoke test con Bruno.
