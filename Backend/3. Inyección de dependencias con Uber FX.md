# Inyección de dependencias con Uber FX

> [!tip] Contexto
> La arquitectura vertical genera decenas de piezas (config, BD, repos, services, handlers). **[Uber FX](https://github.com/uber-go/fx)** las arma automáticamente: en vez de construir a mano `NewProductService(NewProductRepo(db, redis), logger)`, cada pieza declara *qué necesita* y *qué produce*, y FX **resuelve el grafo de dependencias** por ti.

## Conceptos clave

- **`fx.Provide`** → registra un constructor: "yo fabrico esto".
- **`fx.Invoke`** → ejecuta una función con las dependencias resueltas (p. ej. arrancar el server).
- **Dependencia por tipos** → FX inyecta por el tipo de Go, no por nombre.
- **`fx.Lifecycle`** → permite registrar `OnStart`/`OnStop` para recursos (conexiones, servers).
- **Todos los `fx.Provide` forman el grafo**: si falta un constructor o hay un ciclo, la app no arranca y el error lo dice claramente.

## El contenedor (`pkg/container`)

El único lugar donde se conoce toda la aplicación:

```go
package container

import (
	"go.uber.org/fx"

	"mi-backend/internal/modules/auth"
	"mi-backend/internal/modules/user"
	"mi-backend/internal/shared/config"
	"mi-backend/internal/shared/database"
	"mi-backend/internal/shared/logger"
	"mi-backend/internal/shared/redis"
)

type Params struct {
	fx.In // marca: esta struct reúne dependencias que provee el propio módulo
}

func Build(configPath string) *fx.App {
	return fx.New(
		// --- Shared kernel (provee los "servicios base") ---
		fx.Provide(
			func() (string, error) { return configPath, nil },
			config.Load,                 // *config.Config
			logger.New,                  // *zap.Logger
			database.New,                // *gorm.DB
			redis.New,                   // *redis.Client
		),

		// --- Módulos (cada uno provee sus services y registra sus rutas) ---
		user.Module,   // fx.Module de la feature user
		auth.Module,   // fx.Module de la feature auth

		// --- Arranque: invoca el server con todo resuelto ---
		fx.Invoke(server.Module), // registra rutas y app.Listen
	)
}
```

## Cómo se ve un módulo de feature

### `internal/modules/user/module.go`
```go
package user

import "go.uber.org/fx"

// Module expone los constructores y el registro de rutas de la feature.
// FX construye Handler con Service, y Service con Repository automáticamente.
var Module = fx.Module("user",
	fx.Provide(
		NewRepository, // *Repository (necesita *gorm.DB)
		NewService,    // *Service   (necesita *Repository)
		NewHandler,    // *Handler   (necesita *Service)
	),
	fx.Invoke(RegisterRoutes), // func (h *Handler, app *fiber.App) { ... }
)
```

### Constructores con dependencias
```go
// repository.go
func NewRepository(db *gorm.DB) *Repository {
	return &Repository{db: db}
}

// service.go
func NewService(repo *Repository, cache *redis.Client, log *zap.Logger) *Service {
	return &Service{repo: repo, cache: cache, log: log}
}

// handler.go
func NewHandler(svc *Service, val *validator.Validate) *Handler {
	return &Handler{svc: svc, val: val}
}
```

FX ve las firmas y deduce: para construir `*Handler` necesita `*Service` y `*validator.Validate`; para `*Service`, `*Repository`, `*redis.Client` y `*zap.Logger`; y así hasta los nodos raíz. **Nadie construye el grafo a mano.**

> [!warning] El constructor **produce**; no inyecta
> `func NewHandler(svc *Service) *Handler` le dice a FX "necesito un Service y te doy un Handler". Eso es correcto. Lo que **no** debe existir es: `func NewHandler() *Handler { svc := service.NewService(...); ... }` (dios-objeto manual).

## Ciclo de vida: `fx.Lifecycle`

Para recursos que deben cerrarse ordenadamente (conexiones, servers):

```go
func RegisterRoutes(h *user.Handler, app *fiber.App, lc fx.Lifecycle) {
	v1 := app.Group("/api/v1")

	lc.Append(fx.Hook{
		OnStart: func(ctx context.Context) error {
			go app.Listen(":8080")
			return nil
		},
		OnStop: func(ctx context.Context) error {
			return app.Shutdown()
		},
	})
}
```

Así el servidor **arranca con la app FX** y **se apaga con `Ctrl+C`** sin fugas de recursos: FX ejecuta los `OnStop` en orden inverso a los `OnStart`.

## `fx.Annotate` (opcional)

Cuando hay dos constructores que producen el mismo tipo (p. ej. dos `*Repository`), se etiquetan con result tags:

```go
fx.Provide(
	fx.Annotate(user.NewRepository,
		fx.As(new(UserRepository)),   // se inyecta como interfaz
	),
)
```

Con esto `Service` define su dependencia como interfaz `UserRepository` y FX elige la implementación concreta. Es la forma limpia de mantener los módulos desacoplados sobre interfaces → [[1. Arquitectura del proyecto]].

## Datos clave

- `fx.Provide` declara constructores; `fx.Invoke` ejecuta el arranque; `fx.Lifecycle` gestiona recursos.
- El grafo se valida **al arrancar**: dependencias faltantes o ciclos fallan temprano con mensajes claros.
- Cada feature expone su `fx.Module` con sus constructores y rutas.
- `pkg/container` es el único sitio que conoce la app completa.
- Los services piden **interfaces** cuando hay varias implementaciones posibles (`fx.As`).
