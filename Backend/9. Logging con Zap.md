# Logging con Zap

> [!tip] Contexto
> [Uber Zap](https://github.com/uber-go/zap) es el logger estructurado de referencia en Go: logs en JSON (fáciles de indexar en producción) y un presupuesto de asignación bajo. Aquí se inyecta como singleton y se usa en middleware, services y repos.

## Constructor (`internal/shared/logger`)

```go
package logger

import (
	"go.uber.org/zap"
	"go.uber.org/zap/zapcore"
)

func New(env string) (*zap.Logger, error) {
	var cfg zap.Config

	if env == "production" {
		cfg = zap.NewProductionConfig() // JSON + nivel Info
		cfg.EncoderConfig.EncodeTime = zapcore.ISO8601TimeEncoder
	} else {
		cfg = zap.NewDevelopmentConfig() // texto con color + nivel Debug
		cfg.EncoderConfig.EncodeLevel = zapcore.CapitalColorLevelEncoder
	}

	log, err := cfg.Build()
	if err != nil {
		return nil, err
	}
	return log, nil
}
```

> [!tip] Un solo logger
> Todas las piezas reciben el **mismo** `*zap.Logger` por inyección → [[3. Inyección de dependencias con Uber FX]]. Nunca crees loggers sueltos en cada paquete: pierdes configuración y formato único.

## Uso fundamental

```go
log.Info("usuario creado",
	zap.Uint("user_id", user.ID),
	zap.String("tenant", tenantCode),
	zap.Duration("elapsed", elapsed),
)

log.Error("fallo consultando BD", zap.Error(err)) // nunca loguear sin err

// Versión "sugared" para logs con formato simple y menos verboso
sugar := log.Sugar()
sugar.Infof("usuario %d creado en %v", user.ID, elapsed)
```

- **Niveles** (de menor a mayor): `Debug` (dev), `Info` (estado normal), `Warn` (anomalía), `Error` (fallo recuperable/esperado), `Fatal`/`Panic` (no recuperable).
- **Campos estructurados** (`zap.String`, `zap.Uint`, `zap.Error`, `zap.Duration`) mantienen los logs parseables. Nada de `fmt.Sprintf` en el mensaje.
- No loguear **secrets**: nunca passwords, tokens JWT ni datos personales completos (emails → con ofuscación si hace falta).

## Middleware de request logging

Cada request genera una línea de log rastreable por `X-Request-ID`:

```go
func RequestLogger(log *zap.Logger) fiber.Handler {
	return func(c *fiber.Ctx) error {
		start := time.Now()
		requestID := c.GetRespHeader("X-Request-ID") // lo pone el middleware requestid

		err := c.Next()

		fields := []zap.Field{
			zap.String("request_id", requestID),
			zap.String("method", c.Method()),
			zap.String("path", c.Path()),
			zap.Int("status", c.Response().StatusCode()),
			zap.Duration("latency_ms", time.Since(start)),
			zap.String("ip", c.IP()),
		}
		if err != nil {
			// reenviar handlers justo por arriba para no ocultar errores
			fields = append(fields, zap.Error(err))
		}

		if err != nil {
			log.Error("request con error", fields...)
		} else {
			log.Info("request", fields...)
		}
		return err
	}
}
```

## Errores con stack trace

```go
func WrapError(err error) error {
	return errors.Wrap(err, "creando usuario") // pkg/errors → preserva el stack
}
```

Zap puede incluir el stack:

```go
log.Error("operación fallida",
	zap.Error(err),                    // mensaje
	zap.Stack("stack"),                // stack trace completo
)
```

> [!tip] Contexto en producción
> Logs sin `request_id` son casi inútiles para depurar: el patrón es **request_id en cada línea** y correlacionar por ahí. El middleware `requestid.New()` de Fiber ya genera el header → [[4. HTTP con Fiber v2]].

## Datos clave

- Zap produce logs **estructurados** (JSON en producción, colores en dev).
- Singleton inyectado por FX; cada capa lo recibe como dependencia.
- Campos `zap.X` en vez de interpolación de strings.
- Nivel de log configurable por entorno (`production` → Info, `development` → Debug).
- `request_id` en cada línea para correlación.
- Nunca loguear contraseñas, tokens o PII completa.
